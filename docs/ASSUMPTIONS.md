# Assumptions

These are the choices the build proceeds with. Phase 0 left four decisions open. Phase 1 closed them and applied them on the instance. What is still open is at the end.

## Settings

- The repo-root `.env` is parsed with the standard library. The parser strips a UTF-8 BOM, accepts CRLF, skips blank lines and `#` comments, trims whitespace, and strips one matching pair of surrounding quotes. A missing or empty required key fails with the key name and never includes the value.
- `SN_AGENT_USER` is whatever `.env` contains. The confirmed integration-user name is `syn.svc.change_agents`. Phase 0 does not create that user. Phase 1 `seed` does. After that, `cm-agents doctor` prints `agent user: present`.
- The instance URL must match `^https://dev\d+\.service-now\.com$` for its full length. The client will not run against any other host. The URL and the passwords are not written to logs, docs, or git.

## Instance changes

- Phase 0 did not activate plugins, add tables or fields, edit change models, edit standard templates, edit approval definitions, or modify an existing CI.
- Outbound email was off (`glide.email.smtp.active=false`, no active email account). Discovery refuses to create a `SYN-PROBE` change if that stops being true.
- Every `SYN-PROBE` row the probe created was deleted, including approvals, approval groups, change tasks, `task_ci`, service CI links, and conflict rows. The residue queries in `docs/DISCOVERY.md` returned 0.

## Behavior later phases should keep

- Rule-based decisions stay in code. The model is for language and judgment only.
- Date-times are written and read with `display_value=false` and treated as UTC. America/New_York is for policy windows, converted to UTC before the call.
- The integration-user password must be set with `sysparm_input_display_value=true`. On this instance a plain Table API write stores a value basic auth will not accept.
- Phase 1 starts the integration user as Web service access only, with `sn_change_write` and its contained roles (`sn_change_read`, `cmdb_read`, and the other contained read roles). It does not receive `admin`. Phase 3 adds two direct roles, `audit_viewer` and `sn_incident_write`. `itil` was tested and does not grant the journal read. `itil` and `admin` are not granted.
- Agents do not write approval rows. A test helper that approves a change belongs under `tests/` and uses the admin credentials. Agent code does not import it.
- Historical changes and historical releases do not get tasks or approvals. A release that runs carries one implementation task per environment (DEV, TEST, STAGE, PROD). The agent creates no tasks on member changes. The out-of-box normal model still inserts `Implement` and `Post implementation testing` when the change enters Implement, then cancels them (`change_task.state` `4`, label Canceled). The agent cannot delete `change_task` (HTTP 403) and the model is not edited, so those rows stay. Members close with the release, and the close notes name the release change. The 20 seeded releases are not backfilled with tasks.
- `cm-agents discover` is a utility command in the master prompt §7.3. It is the repeatable Phase 0 probe. It is not an agent command.
- There is no `rm_release` table and the plugin that would create it is not on this instance. A release is a normal change named `SYN RELEASE <service> <version>`. Member changes use `parent`. See `docs/DISCOVERY.md` item 10.
- Seeded changes and incidents load through the Import Set API, one row at a time, with business rules off. The loader converts UTC date-times to `America/Los_Angeles` wall time before that call. A timestamp in the repeated Pacific fall-back hour is stored one hour later, so the fixture uses that later instant. Later agent-created changes use the Change API. Each staging table's import set stays in state `loading`. Teardown deletes those sets by staging table name.
- Teardown deletes membership rows only in the six SYN groups and in Change Management, CAB Approval, and eCAB Approval. It then deletes the synthetic users, including the integration user. It does not chase the platform membership `Conditional Script Writer`, which the instance adds back after a delete.
- Affected CI rows (`task_ci`) for the seeded history use that same Import Set path. The Table API insert is aborted by business rule `Change Model: Read only CI (Insert)`. See `docs/DISCOVERY.md` item 9.
- Intake adds affected CIs to a change that is still New with `POST /api/sn_chg_rest/change/{sys_id}/ci`. The body is `cmdb_ci_sys_ids` and `association_type=affected`, and the worker must finish. A body of `cmdb_ci` alone is HTTP 400 for the integration user. The Table API insert into `task_ci` stays blocked.
- Where the master prompt says `caused_by` (§6.6, §8.4, and S07), the instance field is `incident.u_caused_by`. The fixture key stays `caused_by`. Seed writes that reference. `incident.parent` is not the link. Emergency changes still use `change.parent` for the triggering incident. Release members still use `change.parent` for the release change. See `docs/DISCOVERY.md` item 9.
- The generator anchor defaults to midnight UTC on the UTC load date. `--anchor` pins it. The same seed and the same anchor are byte-identical. The anchor is stored on the fixture, in `ground_truth.json`, and in the manifest. Every `opened_at` is before the anchor. Only open-change planned dates may fall in the next 6 weeks.
- `change_authority` in `config/policy.yaml` matches `docs/DISCOVERY.md` item 5. A normal change, at every risk tier, is approved by its assignment group at Assess and by CAB Approval at Authorize. An emergency change is approved by CAB Approval at Authorize. The risk tier does not select the approver.
- `change_request.risk` and `impact` are the agent's score, written with a plain Table API field update. The agent does not call `PATCH /api/sn_chg_rest/change/{sys_id}/risk` and does not call the Risk Calculator. Phase 2 wrote risk `2` and impact `1` on a normal change and read that same pair back after the write, after Assess, after Authorize, and after Scheduled.
- The six `SYN Standard` templates are published through a Standard Change Template Proposal. S01 uses `SYN Standard rotate TLS certificate`. The create ACL on `std_change_record_producer` is unchanged. Freezes stay in policy code.
- Schedule records use `time_zone=US/Eastern` because `America/New_York` is stored empty. Policy math still uses `America/New_York`. The spans store that Eastern wall clock unchanged: Saturday `20110101T220000`–`20110102T040000`, Tuesday `20110104T200000`–`20110104T230000`, and Thursday `20110106T200000`–`20110106T230000`. ServiceNow applies the schedule time zone, including daylight saving. An earlier conflict result looked like a UTC clock because `change.conflict.ci_maint_sched` was false and the demo schedule `Global Infrastructure` (empty condition, Saturday 01:00–04:00) supplied `not_in_maintenance_window`. Seed sets that property to true and sets the demo condition to `nameNOT LIKEsyn-`. Before either write, seed stores the value it just read under `oob_originals` in the manifest, and it does not replace that stored value later. Teardown writes the stored values back after the data rows. On this PDI those stored originals are the Phase 3 pre-change readings, property `false` and an empty condition, because the rows were already at the approved targets. The span text was not rewritten to UTC. Policy code still governs a deployment window. The Deployment agent requires the simulated clock to be inside the approved planned start and end, and it blocks a standard change that sits outside the policy span. It does not treat the OOB maintenance flag as a block. CI overlap and blackout still come from the OOB conflict API. `Blackout Wednesdays (GMT)` comes from ServiceNow's demo data and applies to every `cmdb_ci`. A policy Tuesday-evening Eastern window is Wednesday in GMT, so scheduling moves it. That blackout was not edited. A standard change cannot update `description`, `implementation_plan`, `backout_plan`, or `test_plan`. Those names are `std_change_properties` `readonly_fields`, and business rule `Restrict fields from Standard Change` aborts the whole update. Intake omits them and records the deployment method in a work note.
- The authorization interrupt fires once per approval step. At New a normal change has no approval rows. Moving it to Assess creates only the assignment-group approval. CAB Approval rows are created after that group approves and the change reaches Authorize. One interrupt for the whole authorization would be waiting on rows that do not exist yet. See `docs/DISCOVERY.md` item 5. The master prompt S02 line already says an authorization interrupt at each of those steps and one `go_no_go`, so that sentence was not edited. S03 expects the same two steps, and the human rejects at CAB Approval. S05 expects `cab_approval` at Authorize and no go/no-go. Standard stays pre-authorized. The Phase 2 durability check exits at the first authorization interrupt, the test helper approves every step, and one resume in a new process reaches `go_no_go`.
- Phase 2 did not add a role. At the end of Phase 2 the integration user's only direct role was `sn_change_write`. With that role the agent created normal changes, moved New to Assess, wrote dates, risk, impact, and work notes, associated affected CIs, read conflicts and approvals, and inserted `task_cmdb_ci_service`. A query of `sys_journal_field` by that user returned no rows. Admin could read the notes the agent wrote. `itil` and `admin` were not granted. Phase 3 set the direct roles to `sn_change_write`, `audit_viewer`, and `sn_incident_write`. `audit_viewer` is what makes `sys_journal_field` return work notes and approval comments. `sn_incident_write` is the only role on the `incident.urgency` write ACL. Without it, urgency stays at the default `3` and the priority lookup cannot produce a P1. `itil` was granted in a fresh session and still read zero journal rows. It was revoked. `admin` was not granted. A production design would read journal entries through the record's `work_notes` and `comments` fields, rather than through a cross-table audit role.
- A scenario or agent row has a `correlation_id` that starts with `SYN-` and does not start with `SYN-CHG-`, `SYN-OPEN-`, `SYN-REL-`, or `SYN-INC-`. `remove_scenario_records` deletes those changes and incidents. Deleting the change removes its tasks and affected-CI rows. `counts_in_metrics` is true only for the four seed prefixes. A deployment incident uses the thread id as `correlation_id`, so Phase 5 metrics cannot count it. Change tasks have no separate metric query.
- Teardown compares each baseline table's rows with `sys_created_on` before the seed time to the stored baseline. Rows created after the seed, including the daily `cert_follow_on_task` job, are printed and do not fail the check. The Phase 1 manifest left on this instance has no `seeded_at`. Teardown of that seed still compares totals and prints that `seeded_at` is missing. The next new seed records `seeded_at`. This seed was not torn down and was not re-seeded.

## Phase 5 metric population

Written before the Phase 5 report is computed. `cm_agents/agents/metrics.py` and `build_ground_truth` both follow this rule. They do not share formula code. `cm_agents/rounding.py` (`round_1`, `percent`) is the only shared helper. Each module has its own median. Percentages and hours round to 1 decimal. Python `round` is bankers rounding.

The population is seed records only. A change counts when `correlation_id` starts with `SYN-CHG-`, `SYN-OPEN-`, or `SYN-REL-`. An incident counts when it starts with `SYN-INC-`. `counts_in_metrics` is that test. Scenario rows and ServiceNow demo records are out. Change tasks are not a metric population, including the Canceled Implement and Post implementation testing tasks the normal model adds.

S09 uses the half-open window on `opened_at` from `2025-10-27 00:00:00` UTC inclusive through `2026-10-27 00:00:00` UTC exclusive. That is the 12 months ending at the fixture anchor, not the date the report runs. `cm-agents report metrics` requires `--from` and `--to`. `--period` is only the file name.

- Volume by type, by service, and by month counts every seed change opened in that window, including open changes, canceled changes, and releases opened in the window. The service is the single service name in the change description. The month is the `opened_at` year and month. The fixture `service` field is that same description name.
- Implemented means state Closed (`3`). Canceled (`4`) and a rejected change sent back to New (`-5`) are not implemented.
- The 20 release changes count in volume, success, failure, the emergency ratio, the standard share, lead time, and deployment frequency only when `opened_at` is inside the window. Sixteen are. The four `2025.11.0` releases open at `2025-10-26 02:00:00` UTC and are outside those metrics.
- Change success rate is (`successful` + `successful_issues`) / implemented changes in the window.
- Change failure rate is implemented changes in the window whose `close_code` is `unsuccessful`, or whose `sys_id` is `incident.u_caused_by` on any seed incident, divided by the implemented changes in the window. The caused set is not limited to the window. The instance field is `u_caused_by`.
- Emergency change ratio is emergency changes / every seed change opened in the window.
- Standard change share is standard changes / every seed change opened in the window.
- Change lead time is the median hours from `opened_at` to `work_end` for implemented changes in the window that have a `work_end`.
- Deployment frequency is implemented PROD changes per service per week. Weeks are the window length in seconds divided by 7 days. A release is PROD: its service CI has an empty environment, and a release is a production go-live. A non-release change is PROD only when its CI is in the production class. The fixture word for that class is `prod`. `cmdb_ci.environment` is a choice list of Development, Test, and Production, and it has no stage value. The seed wrote `prod`, `stage`, and `test`. ServiceNow kept `test` as `Test` and stored `prod` and `stage` as empty, so the production class was not readable. The loader writes `Production` and `Test` and leaves stage empty. The current seed's synthetic prod CIs are set to `Production`. `Test` and an empty environment are not PROD. The generator stores `environment` as the constant `prod` on every fixture change, and that value is not on the change record, so it is not the signal. Stage and test CI changes are out.
- MTTR is the median hours from `opened_at` to `resolved_at` for seed incidents whose `u_caused_by` points at a loaded seed change and whose own `opened_at` is inside the window.
- Release on-time rate uses every seed release, not the `opened_at` window, including a rolled-back release. On time means `work_end` <= `end_date`. The four `2025.11.0` releases are in this metric and not in the other change metrics.
- Standard change candidates are normal, not a release, implemented, and opened in the window. The signature is the short description with the case folded and the whitespace collapsed. The group is that signature, the CI `sys_class_name`, and the assignment group name. A group stays when it has at least 10 executions, zero `unsuccessful` closes, and zero caused incidents. Caused uses every seed incident's `u_caused_by`. The proposed template name is `SYN Standard ` plus the signature with a leading `syn ` removed. The report proposes that name. It does not create a template or a proposal.

If `ground_truth.json` and ServiceNow disagree, neither file nor the instance is changed until the side that breaks this rule is identified.
